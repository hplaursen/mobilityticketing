# Lecture 4 — Moodle answers

## Work completed

1. **Unsafe removal:** [`unsafe_change.sql`](../database/postgres/experiments/lecture04/unsafe_change.sql) drops `tickets.product_code` inside a transaction and demonstrates that the old query then fails. Without first adding and backfilling `product_id`, existing tickets would lose their product link. The transaction rolls back. The old-only insert is also shown failing in the final removal rehearsal.
2. **Expand migration:** [`030_expand_product_identity.sql`](../database/postgres/migrations/030_expand_product_identity.sql) assigns each product a UUID, makes it unique, and adds a nullable ticket reference with a `NOT VALID` foreign key. The old code column stays in place. A three-second lock timeout avoids waiting indefinitely for a lock; for a much larger table, plan for DDL locks, table rewrites and a batched backfill. A trigger prevents product IDs from being changed after assignment.
3. **Old application compatibility:** [`old_reader.sql`](../database/postgres/experiments/lecture04/old_reader.sql) and [`old_writer.sql`](../database/postgres/experiments/lecture04/old_writer.sql) use only `product_code`; they work during expansion while `product_id` is nullable.
4. **New writer:** [`new_writer.sql`](../database/postgres/experiments/lecture04/new_writer.sql) looks up the code from the supplied product ID, writes both references, and uses the agreed ticket price rather than copying the current catalogue price. A test supplies a conflicting code; the writer stores the code found through the ID. An unknown ID produces no ticket.
5. **Transitional reader:** [`new_reader.sql`](../database/postgres/experiments/lecture04/new_reader.sql) resolves by ID first and falls back to code when the ID is null. It can read the old tickets before backfill.
6. **Backfill:** [`031_backfill_ticket_product.sql`](../database/postgres/migrations/031_backfill_ticket_product.sql) only fills null IDs. Run it twice; the second run should report `UPDATE 0`. Run the old writer once more and backfill again to cover its late write.
7. **Verification:** [`verify.sql`](../database/postgres/experiments/lecture04/verify.sql) checks null IDs, missing products and mismatched code/ID pairs. `TICKET-3` remains 65 DKK although the DAY catalogue price is 80 DKK. [`mismatch_probe.sql`](../database/postgres/experiments/lecture04/mismatch_probe.sql) shows that direct SQL can create a mismatch while both columns exist, so the compatible writer and deployment verification must prevent it. [`immutable_product_id_probe.sql`](../database/postgres/experiments/lecture04/immutable_product_id_probe.sql) verifies that issued product IDs cannot be changed.
8. **Require the ID:** [`require_before_backfill.sql`](../database/postgres/experiments/lecture04/require_before_backfill.sql) captures why `NOT NULL` fails before backfill. Then [`032_require_ticket_product.sql`](../database/postgres/migrations/032_require_ticket_product.sql) validates the foreign key and makes the ID mandatory. The old writer then fails because it omits `product_id`.
9. **Remove the old reference:** [`remove_legacy.sql`](../database/postgres/experiments/lecture04/remove_legacy.sql) checks dependencies and rehearses dropping `tickets.product_code` without `CASCADE`. In the transaction, the ID-only [reader](../database/postgres/experiments/lecture04/final_reader.sql) and [writer](../database/postgres/experiments/lecture04/final_writer.sql) work; the rehearsal rolls back. `products.code` remains as the catalogue label.

## Rollout decision

Keep both references until all old-only writers have been retired, all tickets pass the final verification, and ID-only readers and writers are deployed. After `product_id` is required and verified, remove `tickets.product_code` in a later deployment. Returning to an old application version after that point requires a compatibility view or a forward migration that recreates and backfills the old column; the old binary cannot simply be restarted. Do not rename or reuse product codes during the overlap period.
